# oat — Checks and verdicts

[← back to the overview](../README.md)

## Checks

125 checks: 112 judge an entity, and 13 judge an operation: the [12 security checks](#security-checks) and [`request.invalid-body-refused`](#validation-of-other-writes). A check that cannot run says so (`did not apply` + `needs`). A check that depends on a broken primitive is `BLOCKED`. A check that ran and stopped is inconclusive, not a pass.

Order is fixed (foundations first) so cascade suppression has a cause to point at. Mutating checks run alone; read-only checks may share in-flight requests under `maxInFlight`.

`depends` is the `dependsOn` list: if any of those already failed **for this entity**, this check is `BLOCKED` rather than reported as a second defect. Suppression is transitive.

### Security checks

These judge an operation rather than an entity: the credential its `security` requires, the schemes it lists, and the sessions behind them. They run in a stage of their own, and their findings name the operation.

- Probes on a read (GET, HEAD, QUERY) run concurrently, before the entity lanes.
- Probes that write, and probes that change a credential (revoke, refresh, failed logins), run after the lanes and before teardown, alone and in order. A write probe targets only a record the run created, with a body that would be harmless if applied: the record's current state cut to what the request body accepts. A DELETE probe never targets a record another step uses: each DELETE operation gets a throwaway record of its own, made by the entity's create as that record's creator, with no children, ledgered and removed by teardown like any create. It is reused while the probes are refused; a probe whose DELETE goes through consumes it, and the next probe makes another. A DELETE on an entity with no create is untested, with the reason. A write operation with no run-created record to target is untested, with the reason.
- An operation whose document declares no security, at the root or on the operation, makes each check stand down as untested: add the `security` by [overlay](configuration.md).
- The probes that need a credential of their own (revoked, refresh-reuse, privileged-field) acquire a dedicated one, a second login or a fresh mint, never the principal's own session. Teardown revokes it.

| `auth.missing-credential-refused` | a secured operation answers a request with no credential with 401 or 403                                                                              | an operation whose security requires a credential                                                 | read before, write after |
| `auth.invalid-credential-refused` | a garbage value, and a real JWT with its signature altered, are refused with 401 for each scheme                                                      | an operation whose security requires a credential                                                 | read before, write after |
| `auth.wrong-scheme-refused`       | a valid credential of a scheme the operation does not list is refused                                                                                 | an operation whose security requires a credential, and a scheme it does not list                  | read before, write after |
| `auth.scope-enforced`             | an API key minted without the operation's scope is refused with 403                                                                                   | an operation that requires a scope, of a scheme a mint recipe issues                              | read before, write after |
| `auth.alternative-accepted`       | each alternative of the operation's security the principal can satisfy, besides the first, works on its own                                           | a read whose security documents a second alternative of one scheme                                | before the lanes         |
| `auth.anonymous-operation-open`   | an operation declared `security: []` answers without a credential; a public write is sent an unreadable body, and passes on any answer but 401 or 403 | an operation whose security lets anonymous callers in                                             | read before, write after |
| `auth.revoked-credential-refused` | a dedicated credential, proven on one read and revoked through the recipe's declared revoke, is then refused with 401 or 403                          | a recipe that declares a revoke, and a GET the credential authenticates                           | after the lanes          |
| `auth.refresh-reuse-refused`      | a dedicated session, rotated through the recipe's refresh, cannot be refreshed again with the refresh token the rotation spent                        | a recipe that declares a refresh, and a GET the credential authenticates                          | after the lanes          |
| `auth.role-enforced`              | a principal marked `readOnly` cannot write: its write to a run-created record in its tenant is refused with 401 or 403                                | a principal marked `readOnly`, and a run-created record in its tenant to write to                 | after the lanes          |
| `auth.cross-tenant-key-refused`   | the peer tenant's API key is refused under the actor's tenant, and accepted under its own                                                             | a peer tenant, and a tenant-scoped GET that takes an API key                                      | before the lanes         |
| `auth.privileged-field-ignored`   | a principal below the highest rank cannot set a property marked `x-privileged`: the record, re-read by its owner, keeps its value                     | a property marked `x-privileged`, a principal ranked below the highest, and a run-created record  | after the lanes          |
| `auth.login-throttled`            | repeated failed logins eventually answer 429                                                                                                          | a login recipe whose login step the document declares, with a request body schema; and the opt-in | after the lanes, opt-in  |

What each needs, and where each route is judged:

- **Per-route guards.** `auth.missing-credential-refused` and `auth.invalid-credential-refused` probe every secured operation. Per-route guard coverage comes from these two: a route that forgets its guard shows there.
- **Credential lifecycle.** `auth.revoked-credential-refused` and `auth.refresh-reuse-refused` sample one route per scheme. A session's revoke and refresh belong to the credential, not to a route, so each anchors once per scheme on the operation the recipe names for that step (a mint's `revoke`, a login's `revoke`, the recipe's `refresh`). It proves the credential on one read: the first GET in document order that takes the scheme alone and whose path the actor's scope fills. With no revoke or refresh declared, the check is untested and says why. It never guesses an operation by its name.
- **Roles.** `auth.role-enforced` needs a principal marked [`readOnly: true`](configuration.md). Rank alone never makes a principal read-only. It differs from `auth.rank-is-monotonic-on-writes`: where every rank may write, the ranks are still monotonic, and only this check fires.
- **Login throttling.** `auth.login-throttled` runs only with the opt-in `checks: { "auth.login-throttled": true }`. It sends failed logins for an identity that does not exist, never a configured principal's, and stops at the first 429 or after 8 attempts. A throttle that counts by address can slow every login from the machine running oat for a while, which is why it is off by default.
- **Targets.** A probe of one record fills each path parameter only from a record the run created of that parameter's own entity: `{token}` in `/invites/{token}/accept` takes an invite the run created, never the table the operation is filed under. With none, the operation is untested with the reason. Each probe kind sends to one target per operation.
- **Open writes.** A 2xx to `auth.anonymous-operation-open`'s unreadable body passes: the route is open, as declared. Whether it validates what it accepts is [`request.invalid-body-refused`](#validation-of-other-writes)'s to judge. The write is taken as applied: what it made is ledgered and removed when its answer names a new id that reads back, and otherwise reported as a record that may remain.
- **Privileged fields.** `auth.privileged-field-ignored` needs a request body property marked [`x-privileged: true`](tags.md#x-privileged). With no marker anywhere, it is untested with "no property is marked x-privileged". A document that lacks the marker takes it by [overlay](configuration.md): `overlay: { schemas: { Table: { properties: { verified: { "x-privileged": true } } } } }`.

### Validation of other writes

The `validation.*-enforced` checks grade creates. `request.invalid-body-refused` grades every other write that takes a JSON request body. Like the security checks, it judges an operation and runs in their stage, after them, alone and in order; its findings name the operation.

| id                             | asserts                                                                                                                                                                                     | needs                                                      |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `request.invalid-body-refused` | one invalid body is refused with a 4xx: the first required property left out, else the first typed property, in document order, sent a value of another type. A 2xx or a 5xx is BACKEND_BUG | a write other than a create that takes a JSON request body |

- **Targets.** A write to one record goes only to a record the run created, as its creator, with the record's current state as the rest of the body. With none, the operation is untested with the reason.
- **Collections.** A write outside a record is not sent: "an action outside a run-created record could apply a side effect the run cannot undo". The one exception is a POST open to all (`security: []`) that the document declares a signup with [`x-fresh-principal`](tags.md), sent anonymously with the rest of its body drawn under the run's seed. Its 2xx is taken as applied: what it made is ledgered and removed when its answer names a new id that reads back, and otherwise reported as a record that may remain. Any other open POST could be a sign-in, where even a malformed body can count toward a lockout, so it is never sent.
- **Open sign-ins.** `auth.anonymous-operation-open` still sends its one unreadable body to every open POST, `auth.login` included: proving the route open is its purpose (`PUBLIC_ROUTE_GUARDED` lives on `auth.login`), and a malformed body answered 400 is the least lockout-prone request there is. This check adds nothing there, so the two never send twice.
- **Credential steps.** An operation a credential recipe names (a login, token, refresh, revoke or mint step, by `operationId` or by method and path) is never sent.
- **Addresses.** An action on a record (a POST that is not its entity's update, an invite say) carries no deliverable address: every email-format value is `oat-nonexistent-<nonce>@example.invalid`, and every URL-format value has an `.invalid` host.

On a typical untagged CRUD document (create, list, item, `page`/`limit`, maybe `sort`):

- Foundations, PATCH/delete, and schema checks usually run.
- The query matrix runs when filter/order/select/search roles resolve.
- Isolation runs only if you configured two principals.
- Spec-as-adversary and tagged behaviour never run — `doctor` says so.

Worked examples of what a finding looks like:

```text
BACKEND_BUG   table   created row missing from GET /tables
              list.read-after-write

BACKEND_BUG   product  PATCH { name } cleared description
              patch.minimality

SECURITY      table    GET /tables/{id} readable with the other tenant's key
              tenant.item-not-readable-cross-tenant

SPEC_BUG      table    x-query.filterable lists "ghost"; filter=ghost.eq.x is 400
              spec.declared-filterable-is-filterable

BACKEND_BUG   table    in() is not the union of the equalities it lists
              filter.in-is-union-of-eq

BACKEND_BUG   table    an illegal filter operator is accepted
              filter.illegal-op-rejected

COVERAGE_GAP  batch    no x-async; receipt treated as the result
              async.reaches-terminal-state
```

## Run-level findings

The run raises these itself, outside any check. They appear in reports like a check's findings.

| id                      | raised when                                                                                                                                                                      | verdict                     |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| `world.seed`            | an entity's cohort could not be seeded: the create was refused, fenced, or ran out of values                                                                                     | `COVERAGE_GAP` or `BLOCKED` |
| `create.does-not-error` | a create answered 5xx for a body generated from the documented schema while seeding                                                                                              | `BACKEND_BUG`               |
| `world.teardown`        | records the run created could not be removed, or teardown stopped on an error                                                                                                    | `COVERAGE_GAP` or `BLOCKED` |
| `teardown.verify-hook`  | `hooks.verifyRemoved` threw                                                                                                                                                      | `COVERAGE_GAP`              |
| `auth.blocked`          | a principal or credential is BLOCKED; the detail names the step (`login`, `signup`, `refresh`) for `<principal>/<scheme>` and the error                                          | `BLOCKED`                   |
| `profile.skip`          | the active profile excluded an operation, so the checks that depend on it stand down; with the create excluded and no existing records to fall back on, the entity is not tested | `COVERAGE_GAP` or `BLOCKED` |
| `net.unreachable`       | the network went down and the remaining entities were skipped                                                                                                                    | `COVERAGE_GAP` or `BLOCKED` |
| `run.interrupted`       | the run was stopped by a signal; what was tested is reported and what oat created is removed                                                                                     | `COVERAGE_GAP`              |
| `run.error`             | testing an entity, or a secondary origin, stopped on an unexpected error                                                                                                         | `BLOCKED`                   |

## Verdicts, skips, and exit codes

| verdict        | meaning                                                              | fails `oat run`? |
| -------------- | -------------------------------------------------------------------- | ---------------- |
| `BACKEND_BUG`  | the handler is wrong                                                 | yes              |
| `SPEC_BUG`     | the document is wrong (or disagrees with the handler)                | yes              |
| `SECURITY`     | isolation/authz failure and `x-tenant` (or equivalent) was declared  | yes              |
| `AMBIGUITY`    | same evidence, but the tenant boundary was only inferred             | yes              |
| `COVERAGE_GAP` | the check could not run; the report names the missing tag or surface | no               |
| `BLOCKED`      | a check this one depends on already failed                           | no               |

Separate from findings:

- **did not apply** — entity never had what `needs` lists (printed in the report, not a pass). Example: no `select` parameter → `select.projection-honoured` did not apply.
- **inconclusive** — the check ran and stopped (empty listing, probe 4xx, no shared filterable field, …). Not a pass. The report prints the reason.

Coverage is split **never** (zero entities could run it) vs **partial** (ran on some entities, skipped on others). A clean run still prints both. "Nothing found" and "nothing was looked for" are different.

Cascade suppression is transitive: one root cause is one finding, not a page of consequences. A blocked check has **not** been verified; re-run after the cause is fixed.

`oat run` exit `1` if any finding has a failing verdict. Gaps and blocked entries do not fail a full run. A targeted run (`--ops`) also exits `1` when any target did not end `passed`.
